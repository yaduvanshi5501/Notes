# 📝 Summary

This demo demonstrates a **complete production-grade Modular RAG pipeline** using Spring AI's `RetrievalAugmentationAdvisor`. Unlike previous examples that focused on individual modules, this project combines multiple pre-retrieval, retrieval, post-retrieval, and generation components into one end-to-end pipeline.

The application ingests Hotel Grand Heaven policy PDFs, indexes them into a MariaDB VectorStore, applies multiple query transformations, expands queries into several variants, retrieves and filters relevant document chunks, augments the prompt with contextual evidence, and streams a grounded response from the LLM.

---

During ingestion the application

- adds source metadata
- splits documents into semantic chunks
- generates embeddings
- stores them in the MariaDB VectorStore

A duplicate-ingestion check prevents the same documents from being indexed multiple times.

# 🔍 Pre-Retrieval Pipeline

Before searching the VectorStore, multiple preprocessing stages improve the query.

### Stage 1 — Hotel Terminology Transformer

A custom transformer replaces common hotel terms with richer search phrases.

Examples include

- `check-in` → `check-in time arrival`
- `parking` → `parking facilities vehicle`
- `Wi-Fi` → `Wi-Fi internet connectivity`

This increases semantic similarity with indexed document chunks.

---

### Stage 2 — RewriteQueryTransformer

After terminology normalization, the rewritten query is generated using a clean `ChatClient`.

```text
Original Query
        ↓
Terminology Expansion
        ↓
RewriteQueryTransformer
        ↓
Search-Optimized Query
```

The transformer uses a neutral client so that the hotel assistant system prompt does not influence retrieval queries.

---

### Stage 3 — MultiQueryExpander

Instead of searching with one query, three semantic variations are generated.

```text
Rewritten Query
        ↓
MultiQueryExpander
        ↓
Query 1
Query 2
Query 3
```

Each variation performs an independent vector search, increasing retrieval recall.

---

# 📄 Retrieval Stage

The application uses a custom `DocumentRetriever`.

Its responsibilities include

- semantic similarity search
- metadata filtering
- top-K selection
- duplicate removal
- noise removal

Configuration includes

- `topK(10)`
- `similarityThreshold`
- optional region filtering

The retriever also detects whether the query targets

- India
- France
- General policies

and automatically restricts retrieval to the relevant PDF.

---

# 🧹 Document Filtering

After retrieval the pipeline cleans the retrieved chunks.

Processing steps include

```text
Retrieved Documents
        ↓
Remove Short Chunks
        ↓
Remove TOC Pages
        ↓
Deduplicate by Document ID
        ↓
Limit Context Size
```

This keeps only the highest-quality document chunks before prompt augmentation.

---

# 📑 Contextual Query Augmentation

After retrieval the application uses

```text
ContextualQueryAugmenter
```

to construct the final prompt.

The augmenter combines

- user question
- filtered document chunks

into one structured context block.

Since

```text
allowEmptyContext(false)
```

is configured, the pipeline refuses to answer if no supporting documents are retrieved, preventing hallucinations.

---

# 💬 Conversation Memory

The pipeline integrates

```text
MessageChatMemoryAdvisor
```

using a `conversationId`.

This enables follow-up questions while keeping conversation history isolated between different users.

---

# 🌊 Streaming Responses

Streaming improves responsiveness for long answers.

# 🚀 Key Takeaways

- The project demonstrates a complete **multi-stage Modular RAG pipeline** using `RetrievalAugmentationAdvisor`.
- Hotel policy PDFs are ingested, enriched with metadata, chunked, embedded, and stored in a MariaDB VectorStore.
- A custom terminology transformer expands hotel-specific vocabulary before retrieval.
- `RewriteQueryTransformer` rewrites queries into retrieval-friendly forms using a clean ChatClient.
- `MultiQueryExpander` generates multiple semantic query variants to improve retrieval recall.
- A custom `DocumentRetriever` performs semantic search, region-aware metadata filtering, and Top-K retrieval.
- Retrieved documents are cleaned by removing short chunks, table-of-contents pages, and duplicate document IDs before limiting the final context.
- `ContextualQueryAugmenter` combines the filtered evidence with the user question to create the final grounded prompt.
- `MessageChatMemoryAdvisor` enables stateful conversations using a conversation ID.
- `ChatClient.stream()` streams the generated response token by token for improved user experience.
- The modular pipeline allows each stage to be independently customized or replaced without affecting the remaining workflow.

The first stage is a **custom QueryTransformer**.

Instead of calling an LLM, it replaces hotel-related words with richer search terms.

## Purpose

Example



---

# Code

```java
QueryTransformer hotelTerminologyTransformer =
        query -> {

    String transformedText = query.text()

        .replaceAll(
            "(?i)check-in",
            "check-in time arrival")

        .replaceAll(
            "(?i)check-out",
            "check-out time departure")

        .replaceAll(
            "(?i)cancellation",
            "cancellation policy refund")

        .replaceAll(
            "(?i)parking",
            "parking facilities vehicle");

    return Query.builder()

            .text(transformedText)

            .build();

};
```

---

# Why Case-Insensitive?

The project uses

```java
(?i)
```

which means

```text
check-in

CHECK-IN

Check-In

check-IN
```

are treated the same.

# Key Takeaways

- The **Pre-Retrieval Pipeline** improves the user query before semantic search begins.
- A custom `QueryTransformer` expands hotel-specific terminology using case-insensitive replacements.
- `RewriteQueryTransformer` uses a clean `ChatClient` to produce retrieval-optimized queries without leaking the hotel assistant system prompt.
- `MultiQueryExpander` generates three semantic variations of the rewritten query, increasing retrieval recall.
- Together, these stages significantly improve the quality of document retrieval before the RAG pipeline enters the retrieval stage. :contentReference[oaicite:0]{index=0}

# 📄 Retrieval Pipeline (Document Retrieval & Region Filtering)

## 📌 Overview

The **Retrieval Stage** is responsible for finding the most relevant document chunks from the Vector Store.

Unlike a simple similarity search, this project performs several intelligent operations before returning documents to the LLM.

The retrieval pipeline performs:

- Region Detection
- Metadata Filtering
- Similarity Search
- Noise Removal
- Document Deduplication
- Context Limiting

These steps ensure that only the most relevant and unique document chunks are passed to the generation stage.

# Key Takeaways

- The **Retrieval Pipeline** is responsible for finding the most relevant document chunks before answer generation.
- Region detection is performed **before query expansion** so that metadata filtering remains consistent across all expanded queries.
- `VectorStoreDocumentRetriever` performs semantic similarity search using `topK(10)` and `similarityThreshold(0.3)`.
- Retrieved results are cleaned by removing short or irrelevant chunks and then deduplicated using document IDs to eliminate overlap from multi-query expansion.
- Only the top five unique document chunks are passed to the generation stage, improving both prompt quality and retrieval efficiency. :contentReference[oaicite:0]{index=0}

# 📄 Generation Pipeline (Context Augmentation & Answer Generation)

## 📌 Overview

The **Generation Stage** is the final phase of the Advanced RAG pipeline.

After the retrieval stage returns the most relevant document chunks, the generation stage prepares the prompt and asks the LLM to generate a grounded response.

This project uses:

- ContextualQueryAugmenter
- RetrievalAugmentationAdvisor
- Chat Memory
- System Prompt
- ChatClient Streaming

Unlike a normal chatbot, the LLM does **not** answer using only its own knowledge. Instead, it answers using the retrieved hotel policy documents.

# 📄 RAGPipelineService Architecture

## 📌 Overview

`RAGPipelineService` is the core implementation of the **Advanced Multi-Stage RAG Pipeline**.

It combines every stage of Retrieval-Augmented Generation into a single workflow using Spring AI's `RetrievalAugmentationAdvisor`.

Instead of performing only semantic search, this service builds a complete pipeline consisting of:

- Data Ingestion
- Query Transformation
- Query Rewriting
- Multi Query Expansion
- Region-aware Retrieval
- Context Augmentation
- Conversation Memory
- Streaming Answer Generation

# Constructor

The constructor initializes every major Spring AI component.

---

## Code

```java
public RAGPipelineService(

        ChatClient.Builder chatClientBuilder,

        VectorStore vectorStore,

        ChatModel chatModel) {

    this.chatMemory =

            MessageWindowChatMemory

                    .builder()

                    .build();

    this.chatClient =

            chatClientBuilder

                    .defaultAdvisors(

                        MessageChatMemoryAdvisor

                            .builder(chatMemory)

                            .order(1)

                            .build())

                    .defaultAdvisors(

                        SimpleLoggerAdvisor

                            .builder()

                            .order(10)

                            .build())

                    .build();

    this.vectorStore = vectorStore;

    this.chatModel = chatModel;

}
```

# Key Takeaways

- `RAGPipelineService` is the central service that implements the complete **Advanced Multi-Stage RAG Pipeline**.
- It initializes and coordinates `ChatClient`, `ChatModel`, `VectorStore`, `ChatMemory`, and logging advisors.
- A separate `ChatModel` is used for query transformation to prevent the hotel assistant system prompt from influencing rewritten or expanded search queries.
- The service orchestrates all six stages of the RAG workflow through `RetrievalAugmentationAdvisor`, from query preprocessing to streaming answer generation.
- The architecture demonstrates a production-ready, modular RAG implementation that is significantly more flexible and extensible than a basic `QuestionAnswerAdvisor`-based solution. :contentReference[oaicite:0]{index=0}
