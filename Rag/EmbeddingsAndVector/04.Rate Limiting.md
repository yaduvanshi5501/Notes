# 🤔 What Is Rate Limiting?

**Rate Limiting** is a traffic control mechanism that restricts how many times a method or API can be executed within a specified time window.

Its primary goal is to ensure that your application **does not exceed the request quota** imposed by an external service.

Instead of reacting to an error such as **HTTP 429 (Too Many Requests)**, a Rate Limiter prevents the application from sending requests too quickly in the first place.

---

# Why Do We Need Rate Limiting?

Most external AI providers enforce request limits.

Examples:

| Provider | Example Request Limit |
|-----------|----------------------:|
| GitHub Models | ~15 requests/minute |
| OpenAI Free Tier | ~3 requests/minute |
| Azure OpenAI | Depends on deployment quota (often hundreds of requests/minute) |

If an application sends requests faster than the allowed quota, the provider rejects them.

```text

```

---

# Consequences

Without rate limiting:

- API requests fail.
- Document ingestion stops midway.
- Some data may already be stored.
- Processing must be restarted.
- Application reliability decreases.

# Example Scenario

Suppose an application generates embeddings for every document chunk.

```java
for (Document chunk : chunks) {
    vectorStore.add(List.of(chunk));
}
```

Each call to `vectorStore.add()` generates embeddings.

If hundreds of chunks are processed, hundreds of API requests may be sent within seconds.

# Approaches to Rate Limiting

There are several ways to control request rates.

---

# Approach A – `Thread.sleep()`

The simplest solution is to pause after every request.

```text
Request

↓

Wait

↓

Request

↓

Wait
```

Example:

```java
for (Document chunk : chunks) {
    vectorStore.add(List.of(chunk));
    Thread.sleep(4000);
}
```

---

## Advantages

- Very simple
- Easy to understand

---

## Limitations

- Blocks the current thread.
- Wastes server resources.
- Poor scalability.
- Difficult to maintain.
- Hard-coded timing values.
- No monitoring or metrics.
- Does not work well with concurrent requests.

---

# Approach B – Batch Processing + Sleep

Instead of sending one document at a time, multiple documents are grouped together.

```text
5 Documents

↓

One API Call

↓

Wait

↓

Next Batch
```

This reduces the total number of API requests.

---

## Advantages

- Better than individual requests.
- Fewer API calls.

---

## Limitations

- Still blocks threads.
- Still relies on manual delays.
- No automatic retries.
- No observability.
- Difficult to adjust dynamically.

---

# Approach C – Resilience4j RateLimiter ⭐

The recommended production approach.

Instead of manually waiting, Resilience4j controls how frequently a method can execute.

```text
Application

↓

RateLimiter

↓

External API
```

The application code remains clean while configuration controls the request rate.

---

# How Resilience4j Works

A method is annotated with:

```java
@RateLimiter
```

Before execution:

```text
Request

↓

RateLimiter

↓

Allowed?

↓

Yes

↓

Execute Method
```

If the limit has already been reached:

```text
Request

↓

RateLimiter

↓

Limit Reached

↓

Wait or Reject
```

depending on the configured timeout.

---

# Configuration

The RateLimiter is configured externally in `application.properties`.

Typical settings include:

| Property | Purpose |
|-----------|---------|
| `limitForPeriod` | Maximum calls allowed in one time window |
| `limitRefreshPeriod` | Duration of the time window |
| `timeoutDuration` | Maximum time a request waits for permission |

This allows changing rate limits without modifying Java code.

---

# Understanding the Configuration

## limitForPeriod

Specifies the maximum number of permitted requests.

Example:

```text
12 Calls
```

---

## limitRefreshPeriod

Defines how often the counter resets.

Example:

```text
60 Seconds
```

After sixty seconds, the RateLimiter starts counting from zero again.

---

## timeoutDuration

Determines how long a blocked request waits before giving up.

If a permit becomes available within this period, the request proceeds.

Otherwise, it fails.

---

# Why Configure 12 Instead of 15?

Suppose the provider allows:

```text
15 Requests

per

60 Seconds
```

Sending exactly fifteen requests every minute may still occasionally exceed the provider's limit because of timing differences between your application and the provider.

Using:

```text
12 Requests
```

provides a safety buffer that reduces the chance of accidental quota violations.

# Best Practices

- Use `@RateLimiter` for all external AI service calls that are subject to quotas.
- Configure limits based on the provider's documented quotas.
- Leave a safety buffer below the maximum allowed rate.
- Combine RateLimiter with Retry for transient failures.
- Monitor rate-limiting metrics in production.
- Avoid `Thread.sleep()` in production applications.

# 🔥 Summary

Rate Limiting protects applications from exceeding the request quotas enforced by external services such as LLM and embedding providers. Instead of allowing unrestricted API calls that may result in **HTTP 429 (Too Many Requests)** errors, a RateLimiter controls how frequently requests are executed within a defined time window. While simple approaches such as `Thread.sleep()` can limit request rates, they block threads and do not scale well. **Resilience4j RateLimiter** provides a production-ready solution by managing request frequency through external configuration, improving reliability, scalability, and maintainability. In Spring AI, rate limiting is particularly important during operations such as embedding generation, vector store ingestion, and Retrieval-Augmented Generation (RAG), where large numbers of API calls are common.
