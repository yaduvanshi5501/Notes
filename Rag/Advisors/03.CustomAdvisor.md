# 📚 Custom Advisors in Spring AI

> **Custom Advisors** allow developers to create their own middleware components that intercept, inspect, modify, or block AI requests and responses. They provide a clean way to implement business rules, security, logging, prompt enrichment, and response processing without changing application code.

# 🤔 Why Do We Need Custom Advisors?

As AI applications grow, every `ChatClient` call usually needs additional logic.

Without Advisors, every API may require:

- ❌ System prompts
- ❌ Safety validation
- ❌ Prompt enrichment
- ❌ Logging
- ❌ Error handling
- ❌ Context injection
- ❌ Output formatting

This leads to:

- Duplicate code
- Difficult maintenance
- Inconsistent AI behavior

Example:

```text
Controller A
 ├── Logging
 ├── Safety
 └── Prompt Modification

Controller B
 ├── Logging
 ├── Safety
 └── Prompt Modification

Controller C
 ├── Logging
 ├── Safety
 └── Prompt Modification
```

The same logic is repeated everywhere.

---

# ✅ The Solution: Custom Advisors

Instead of writing common logic in every controller, write it **once** inside a Custom Advisor.

```text
Controller

      │

      ▼

Custom Advisor

      │

      ▼

LLM
```

Now every request automatically passes through the advisor.

Benefits:

- Centralized logic
- Reusable code
- Cleaner controllers
- Easy maintenance
- Consistent AI behavior

---

# 🧠 What is a Custom Advisor?

A **Custom Advisor** is a user-defined interceptor created by the developer.

It executes:

- **Before the LLM call (Pre-processing)**
- **After the LLM call (Post-processing)**

Unlike built-in advisors provided by Spring AI, Custom Advisors allow you to implement your own business-specific logic.

---

# 🔄 What Can a Custom Advisor Do?

## Before Calling the LLM

A Custom Advisor can:

- Inspect the prompt
- Modify the prompt
- Add system instructions
- Inject user context
- Validate input
- Block unauthorized requests
- Perform rate limiting
- Sanitize user input

---

## After Receiving the Response

A Custom Advisor can:

- Inspect the AI response
- Remove sensitive information
- Format the response
- Add metadata
- Log results
- Transform output

---

# 🏗 Execution Flow

```text
Application

      │

      ▼

Custom Advisor

      │

      ├── Pre-processing
      │     • Inspect request
      │     • Modify prompt
      │     • Validate input
      │
      ▼

Advisor Chain / LLM

      ▲

      │

      ├── Post-processing
      │     • Inspect response
      │     • Filter output
      │     • Add metadata
      │

      ▼

Application
```

# Types of Custom Advisors

Spring AI supports two types of advisors.

| Type | Interface | Purpose |
|------|-----------|---------|
| Synchronous | `CallAdvisor` | Normal request-response interactions |
| Streaming | `StreamAdvisor` | Token-by-token streaming responses |

---

# 1. CallAdvisor

`CallAdvisor` is used for **non-streaming** AI requests.

It processes a complete request and waits until the model returns a complete response.

Typical use cases:

- Input validation
- Prompt enrichment
- Authorization
- Policy enforcement
- Rate limiting
- Response modification

---

# 2. StreamAdvisor

`StreamAdvisor` is used when responses are streamed token by token.

Instead of returning one response, it returns a stream of responses.

Best suited for:

- Live chat
- AI typing effect
- Streaming UIs
- Incremental filtering
- Real-time moderation

---

# Advisor API Hierarchy

All advisor interfaces are located in:

```text
org.springframework.ai.chat.client.advisor.api
```

Hierarchy:

```text
Advisor
      │
      ├───────────────┐
      │               │
CallAdvisor     StreamAdvisor
```

---

# Root Interface: Advisor

Every advisor ultimately implements the `Advisor` interface.

It provides two important methods.

## getName()

Returns a unique advisor name.

Used for:

- Logging
- Debugging
- Monitoring
- Observability

---

## getOrder()

Determines where the advisor executes in the chain.

Lower value

↓

Higher priority

---

# CallAdvisor

Main method:

```java
adviseCall(...)
```

Responsibilities:

- Inspect request
- Modify request
- Call next advisor
- Receive response
- Modify response
- Return final response

Important:

If `nextCall()` is **not called**, the request stops there and never reaches the LLM.

This allows an advisor to block requests completely.

---

# StreamAdvisor

Main method:

```java
adviseStream(...)
```

Works similarly to `CallAdvisor`, but returns a stream of responses instead of a single response.

---

# Advisor Chain

Advisors execute sequentially.

Example:

```text
Logging Advisor

↓

Memory Advisor

↓

Safety Advisor

↓

LLM
```

Each advisor decides whether to:

- Continue
- Modify
- Block

---

# CallAdvisorChain

Used for synchronous advisors.

Provides:

- `nextCall()` → Pass request to next advisor or LLM
- `getCallAdvisors()` → Returns all advisors in the chain

---

# StreamAdvisorChain

Used for streaming advisors.

Provides:

- `nextStream()` → Pass stream request forward
- `getStreamAdvisors()` → Returns streaming advisors

---

# How to Create a Custom Advisor

Creating a Custom Advisor involves four simple steps.

## Step 1

Implement either:

- `CallAdvisor`
- `StreamAdvisor`
- or both

---

## Step 2

Override:

- `adviseCall()` or `adviseStream()`

This is where your interception logic is written.

---

## Step 3

Override:

```java
getOrder()
```

Controls execution order.

---

## Step 4

Override:

```java
getName()
```

Returns the advisor's unique identifier.

---

# Request Processing

Inside `adviseCall()` you usually:

1. Read the request
2. Modify the prompt
3. Create a new request
4. Call `nextCall()`

Example flow:

```text
Read Prompt

↓

Modify Prompt

↓

Create New Request

↓

nextCall()

↓

LLM
```

---

# Response Processing

After `nextCall()` returns:

```text
Receive Response

↓

Read Output

↓

Modify Output

↓

Return Response
```

---

# Registering Custom Advisors

Spring AI provides three ways to register advisors.

## 1. Default Advisor

Registered during ChatClient creation.

Runs for every request.

Best for:

- Logging
- Memory
- Compliance
- Prompt enrichment

---

## 2. Per-Call Advisor

Registered using:

```java
.advisors(...)
```

Runs only for one request.

Useful when only a specific endpoint requires additional processing.

---

## 3. Multiple Advisors

Multiple advisors can be registered together.

Spring AI automatically creates an Advisor Chain.

---

# Advisor Chaining

Example:

```text
Logging

↓

Memory

↓

Safety

↓

LLM
```

Each advisor calls:

```text
nextCall()
```

to continue execution.

Without calling `nextCall()` the request stops.

---

# Advisor Ordering

Execution depends on `getOrder()`.

Example:

| Advisor | Order |
|----------|------:|
| Logging | 0 |
| Memory | 10 |
| Safety | 20 |

---

## Request Flow

```text
Logging

↓

Memory

↓

Safety

↓

LLM
```

---

## Response Flow

```text
LLM

↓

Safety

↓

Memory

↓

Logging
```

Lower values execute first during requests and last during responses.

---

# Best Practices

- Keep each advisor responsible for one task.
- Register common advisors using `defaultAdvisors()`.
- Use per-call advisors only when necessary.
- Always call `nextCall()` unless intentionally blocking the request.
- Assign unique order values.
- Give every advisor a meaningful name.
- Keep business logic separate from controller code.

---

# 📝 Quick Revision

- Custom Advisors are user-defined interceptors.
- They execute before and after the LLM.
- They centralize business logic.
- `CallAdvisor` is used for synchronous requests.
- `StreamAdvisor` is used for streaming responses.
- `Advisor` is the root interface.
- `nextCall()` forwards the request through the chain.
- Not calling `nextCall()` blocks the request.
- `getOrder()` controls execution order.
- Lower order values execute first.
- Responses travel back through the chain in reverse order.
- Advisors can be registered globally or per request.

---

# 🔥 Summary

Custom Advisors extend Spring AI by allowing developers to create reusable middleware that intercepts AI requests and responses. They can inspect, modify, validate, enrich, or block prompts before they reach the LLM, and post-process responses after generation. Built on the `Advisor` API with `CallAdvisor` and `StreamAdvisor`, they execute through an ordered Advisor Chain, making AI applications cleaner, more maintainable, and enterprise-ready by centralizing cross-cutting concerns such as security, logging, prompt engineering, and governance.
