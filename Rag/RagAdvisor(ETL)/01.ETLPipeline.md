# 📝 Summary

Retrieval-Augmented Generation (RAG) enables a Large Language Model (LLM) to answer questions using external knowledge instead of relying only on its pretrained data. Before a document can participate in retrieval, it must pass through an **ETL (Extract, Transform, Load) pipeline**. This pipeline prepares raw documents for semantic search by converting them into vector embeddings and storing them inside a VectorStore.

Spring AI standardizes this workflow by representing every piece of content as a `Document` object. Regardless of whether the source is a PDF, Word document, text file, or webpage, the ETL pipeline always operates on `Document` instances, making the ingestion process consistent across different document types.

---

## ETL Pipeline in Spring AI

Spring AI divides document ingestion into three independent phases.

| Phase | Interface | Java Functional Interface | Responsibility |
|--------|-----------|---------------------------|----------------|
| Extract | `DocumentReader` | `Supplier<List<Document>>` | Reads raw content and creates `Document` objects |
| Transform | `DocumentTransformer` | `Function<List<Document>, List<Document>>` | Splits, enriches, filters, or modifies documents |
| Load | `DocumentWriter` | `Consumer<List<Document>>` | Embeds and stores documents inside the VectorStore |

Each phase has a single responsibility, making the ingestion pipeline modular and reusable.

---

## Phase 1 – Extract

The extraction phase is responsible for reading raw documents from their original source.

In this demo, `PagePdfDocumentReader` reads every PDF page and converts it into one or more Spring AI `Document` objects.

```text
PDF
      ↓
PagePdfDocumentReader
      ↓
List<Document>
```

When multiple PDF files are uploaded, the application creates a new reader for each file and collects all extracted documents into a single list.

During extraction, additional metadata is also attached.

```java
document.getMetadata().put("source", pdf.getFilename());
```

Adding the filename as metadata allows future filtering during retrieval.

Example:

```text
source = india-hotel-policy.pdf
```

Later, retrieval can search only documents originating from a specific file.

---

## Phase 2 – Transform

After extraction, documents are transformed before being stored.

Large page-sized documents are unsuitable for embeddings because they contain too much information.

`TokenTextSplitter` divides every page into smaller semantic chunks.

```text
Large Document
        ↓
TokenTextSplitter
        ↓
Chunk 1
Chunk 2
Chunk 3
Chunk 4
```

The splitter attempts to preserve sentence boundaries while producing chunks of approximately 800 tokens.

Using

```java
new TokenTextSplitter(true)
```

preserves newline separators, improving document readability and semantic structure.

Since `TokenTextSplitter` implements `DocumentTransformer`, it follows the standard transformation contract.

```text
List<Document>
        ↓
Transform
        ↓
List<Document>
```

Other transformers such as metadata enrichers can be added to the same pipeline because they implement the same interface.

---

## Phase 3 – Load

The final phase stores transformed documents inside the VectorStore.

```java
vectorStore.add(chunks);
```

Although only a single method is called, Spring AI performs several operations internally.

```text
Chunks
      ↓
EmbeddingModel
      ↓
Generate Embeddings
      ↓
Store Text
      ↓
Store Metadata
      ↓
Store Vector
      ↓
VectorStore
```

Each chunk is converted into a high-dimensional embedding vector, and the following information is persisted together:

- Original chunk text
- Embedding vector
- Metadata
- Document identifier

These stored vectors are later used for semantic similarity search during Retrieval-Augmented Generation.

## Complete ETL Workflow

The entire ingestion process can be visualized as follows.

```text
PDF Files
      ↓
PagePdfDocumentReader
      ↓
List<Document>
      ↓
Add Metadata
      ↓
TokenTextSplitter
      ↓
Document Chunks
      ↓
VectorStore.add()
      ↓
Embedding Generation
      ↓
MariaDB VectorStore
```

Each stage performs one dedicated responsibility before passing its output to the next stage, creating a clean and extensible ETL pipeline.

---

## Why Spring AI Uses Functional Interfaces

Spring AI models every ETL stage as a Java Functional Interface.

- `DocumentReader` supplies documents.
- `DocumentTransformer` transforms documents.
- `DocumentWriter` consumes documents.

Because every component follows a common contract, different readers, transformers, and writers can be chained together without changing the overall pipeline.

Example:

```text
DocumentReader
        ↓
TokenTextSplitter
        ↓
KeywordMetadataEnricher
        ↓
SummaryMetadataEnricher
        ↓
VectorStore
```

This modular architecture allows developers to build custom ingestion pipelines by simply replacing or adding new implementations.

---

## 🚀 Key Takeaways

- RAG requires documents to pass through an ETL pipeline before retrieval.
- Spring AI represents all content as `Document` objects.
- `DocumentReader` extracts raw content from external sources.
- `PagePdfDocumentReader` converts PDF pages into `Document` objects.
- Metadata such as the source filename can be added during extraction.
- `DocumentTransformer` modifies documents before storage.
- `TokenTextSplitter` divides large documents into semantic chunks.
- `DocumentWriter` stores transformed documents inside the VectorStore.
- `vectorStore.add()` automatically generates embeddings and persists vectors with metadata.
- The ETL pipeline is modular because every phase follows a Java Functional Interface contract.
