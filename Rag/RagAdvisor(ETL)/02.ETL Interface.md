# 📝 Summary

Spring AI prepares documents for Retrieval-Augmented Generation (RAG) using an **ETL (Extract, Transform, Load) pipeline**. Every stage operates on the `Document` object, making the ingestion process consistent regardless of whether the source is a PDF, Word document, text file, or JSON.

The ETL pipeline is modeled using three Java Functional Interfaces:

| Phase | Interface | Responsibility |
|--------|-----------|----------------|
| Extract | `DocumentReader` | Reads raw content and converts it into `Document` objects |
| Transform | `DocumentTransformer` | Splits, enriches, or modifies documents before storage |
| Load | `DocumentWriter` | Generates embeddings and stores documents inside the VectorStore |

---

## 📥 Extract Phase

The extraction phase converts raw files into Spring AI `Document` objects.

In this course, `PagePdfDocumentReader` is used because hotel policy documents are organized page by page, making every page an independent `Document`. During extraction, metadata such as the source filename is added so the retriever can later filter or cite the originating document.

```text
PDF
      ↓
PagePdfDocumentReader
      ↓
List<Document>
```

Spring AI also provides readers such as `ParagraphPdfDocumentReader`, `TikaDocumentReader`, `TextReader`, and `JsonReader` for different document formats.

---

## 🔄 Transform Phase

The transformation phase prepares documents for AI processing.

The first transformation is metadata enrichment, where custom metadata such as `source`, `region`, `department`, or `version` can be attached to every document. This metadata remains available throughout the RAG pipeline and supports filtering and document traceability.

The second transformation is text chunking. Since embedding models and LLMs have token limits, large documents are divided into smaller semantic chunks using `TokenTextSplitter`.

```text
Documents
      ↓
Metadata
      ↓
TokenTextSplitter
      ↓
Document Chunks
```

`TokenTextSplitter` creates approximately 800-token chunks, preserves sentence boundaries, and automatically copies parent metadata into every child chunk.

Spring AI also provides transformers such as `KeywordMetadataEnricher`, `SummaryMetadataEnricher`, and `ContentFormatTransformer`, allowing additional preprocessing before storage.

---

## 📦 Load Phase

The final stage stores processed chunks inside the VectorStore.

Calling

```java
vectorStore.add(chunks);
```

automatically generates embeddings for every chunk, stores the original text, preserves metadata, and writes the vectors into the configured vector database.

```text
Chunks
      ↓
Embedding Model
      ↓
1536-D Vector
      ↓
VectorStore
```

Because every VectorStore implements `DocumentWriter`, applications can switch from MariaDB to PostgreSQL, Chroma, or other supported vector databases by changing only the dependency and configuration, without modifying application code.

---

## 🔗 Complete ETL Workflow

```text
Raw Documents
      ↓
DocumentReader
      ↓
Document
      ↓
Metadata Enrichment
      ↓
TokenTextSplitter
      ↓
Document Chunks
      ↓
Embedding Model
      ↓
VectorStore
      ↓
Ready for Semantic Retrieval
```

The output of one phase becomes the input of the next, creating a clean and modular ingestion pipeline that can easily be extended with additional readers, transformers, or writers.

---

## 🚀 Key Takeaways

- Spring AI models document ingestion as an ETL pipeline.
- Every document is represented as a `Document` object.
- `DocumentReader` extracts raw content into `Document` objects.
- `PagePdfDocumentReader` is used for page-wise PDF extraction.
- `DocumentTransformer` performs metadata enrichment and text chunking.
- `TokenTextSplitter` creates LLM-friendly chunks while preserving metadata.
- Metadata enables filtering, citations, and traceability during retrieval.
- `DocumentWriter` stores embedded documents inside the VectorStore.
- `vectorStore.add()` automatically generates embeddings and persists vectors.
- The ETL architecture is modular because all readers, transformers, and writers follow Java Functional Interface contracts.
